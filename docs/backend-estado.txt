ESTADO DEL BACKEND — B-Side Club (TPO Plataforma web para pequeños comercios)
Stack: Node.js + Express + Prisma (PostgreSQL/Supabase) + JWT. JavaScript plano, sin TypeScript.
Base URL local: http://localhost:3000/api

Numeración según las funciones principales que pide el enunciado del TPO.

IMPORTANTE — API key en todos los pedidos:
Todos los pedidos a /api/* requieren el header "x-api-key" con la clave
configurada en la variable de entorno API_KEY. La unica excepcion es
GET /api/health, que queda publico. Los archivos estaticos de /uploads
tampoco la piden (no estan bajo /api). Sin ese header la respuesta es
401 { "error": "API key inválida o faltante" }, antes de llegar a
cualquier ruta. El detalle de esta capa y de las otras dos esta en la
seccion 9.

============================================================
1. SITIO PUBLICO (visitante, sin login)
============================================================
1.1 Informacion general del comercio
    GET /api/store-info
    Nombre, descripcion, direccion, telefono, mail, instagram, whatsapp,
    horario (JSON).

1.2 Visualizar productos y/o servicios ofrecidos
    GET /api/productos
    GET /api/productos/:id  (detalle con categoria e imagenes, ordenadas
    por el campo "orden" de cada imagen)
    Solo muestra productos con esActivo=true — nunca los dados de baja.
    Vale para las dos rutas, tambien para el detalle por id: un producto
    inactivo devuelve 404 al visitante, igual que uno que no existe (no
    decimos "existe pero no te lo mostramos", porque eso ya seria delatarlo).
    El panel, con token, si los ve: los necesita para poder reactivarlos.

1.3 Buscar publicaciones
    GET /api/productos?q=texto
    Busca por nombre y descripcion, sin distinguir mayusculas/minusculas.

1.4 Filtrar publicaciones por categoria
    GET /api/productos?categoriaId=N
    (tambien soporta ?destacado=true para la seccion de destacados/home)

1.5 Consultar informacion de contacto
    Incluida en GET /api/store-info (telefono, mail, instagram, whatsapp).

1.6 Enviar consultas al comercio
    POST /api/consultas — nombre, email (validado), asunto, mensaje
    obligatorios; telefono y productoId opcionales. Queda guardada con
    estado="pendiente".

Paginacion del catalogo: GET /api/productos soporta page y pageSize
(default 12, maximo 60). Devuelve { productos, page, pageSize, total,
totalPages }.

============================================================
2. REGISTRO E INICIO DE SESION (administrador)
============================================================
2.1 Registrarse
    POST /api/auth/register — crea el primer usuario (queda como
    super_admin). El resto del staff se suma via invitacion (seccion 4),
    no por este endpoint.
    Datos minimos pedidos: nombre, apellido, mail, telefono, contraseña.
    Mail duplicado rechazado (constraint unico en la base).

2.2 Iniciar sesion
    POST /api/auth/login — devuelve { token, user }. El JWT vence a
    los 7 dias (JWT_EXPIRES_IN en .env).

2.3 Cerrar sesion
    POST /api/auth/logout (protegida) — el token es stateless, lo
    descarta el frontend; este endpoint solo confirma la accion.

2.4 Recuperar contraseña
    POST /api/auth/forgot-password — genera un token valido 30 minutos
    y lo manda por mail (o lo loguea por consola si no hay SMTP
    configurado). Respuesta identica exista o no el mail, para no
    filtrar que usuarios estan registrados.
    POST /api/auth/reset-password — valida token + contraseña nueva
    y actualiza el hash.

2.5 Modificar sus datos personales
    GET /api/auth/me y PUT /api/auth/me (protegidas).

Validaciones aplicadas: formato de mail (regex) y contraseña minima de
6 caracteres, tanto en registro como en reset y aceptar invitacion.

3. ADMINISTRACION DE INFORMACION INSTITUCIONAL
============================================================
PUT /api/store-info (protegida: cualquier rol de staff)
Upsert sobre la fila unica de la tabla StoreInfo (id=1): nombre,
descripcion, direccion, telefono, redes sociales (instagram/whatsapp)
y horarios de atencion.

============================================================
4. ADMINISTRACION DE PRODUCTOS Y SERVICIOS
============================================================
4.1 Crear publicaciones
    POST /api/productos (protegida) — valida campos requeridos y que
    la categoria exista.

4.2 Modificar publicaciones
    PUT /api/productos/:id (protegida) — edita los campos del producto.
    Acepta solo una lista blanca de campos (nombre, anio, precio, stock,
    estado_stock, condicion, destacado, esActivo, descripcion, categoriaId).
    Cualquier otra cosa que venga en el body se ignora: antes se pasaba el
    body completo a Prisma y se podia mandar "id", que reasignaba la clave
    primaria del producto.
    Valida que anio/stock/categoriaId sean numeros y que la categoria exista,
    y devuelve 400 si no — antes esos casos salian como error interno.

4.3 Eliminar publicaciones
    DELETE /api/productos/:id (protegida) — borra el producto y sus
    imagenes en cascada.

4.4 Activar o desactivar publicaciones
    Se logra con PUT /api/productos/:id mandando { esActivo: false }.
    No hay un endpoint PATCH separado para esto — es la misma via que
    editar cualquier otro campo.

4.5 Imagenes de cada publicacion (multiples, con portada)
    POST /api/productos/:id/imagenes (protegida) — sube hasta 5
    imagenes reales con multer. El orden sigue la secuencia existente
    del producto (no pisa la portada al agregar una tanda nueva).
    Los archivos NO se guardan en el servidor: van a Supabase Storage
    (bucket "productos", publico) y en la base queda su URL completa.
    Antes se escribian en una carpeta uploads/, pero eso dejo de servir
    cuando el backend paso a correr como funcion de Netlify: una funcion
    se levanta y se muere por cada pedido, no tiene disco propio.
    Hacen falta SUPABASE_URL y SUPABASE_SERVICE_ROLE_KEY en el .env.
    PATCH /api/imagenes/:id (protegida) — cambia el campo "orden" de
    una imagen ya subida, para reordenar cual queda como portada.
    DELETE /api/imagenes/:id (protegida) — borra el registro y el
    archivo fisico en /uploads.

4.6 Productos precargados para demostrar busqueda/filtros/navegacion
    Seed con 22 productos (el minimo que pide la consigna es 20),
    repartidos en las 4 categorias.

Cada producto guarda: nombre, categoria, imagenes, descripcion, precio
(nullable = "a consultar"), y estado de disponibilidad (enum: disponible,
ultima_unidad, reservado, a_consultar, vendido) ademas de esActivo y
destacado.

Administrador (repartido en 3 roles del sistema: super_admin,
administrador, vendedor — el enunciado pide un solo rol "administrador",

- Gestionar categorias: seccion 5 (los 3 roles).
- Gestionar consultas: seccion 7 (los 3 roles).
- Administrar informacion del comercio: seccion 3 (los 3 roles).

Reglas de permisos especiales, resueltas a mano porque dependen del
usuario DESTINO y no solo de quien hace el pedido:
- Invitar usuarios nuevos: solo super_admin y administrador.
- Nadie puede editar ni eliminar al super_admin.
- Nadie puede asignarse (ni asignarle a otro) el rol super_admin.
- Solo el super_admin puede eliminar a un administrador.

Invitaciones y gestion de usuarios (como se suma el resto del equipo):
POST   /api/invitacion            Invita por mail con un rol. Token
                                   valido 7 dias. Solo puede haber UNA
                                   invitacion vigente por mail: si ya hay una
                                   pendiente sin vencer devuelve 409 y hay que
                                   revocarla primero. Antes se podian emitir
                                   varios tokens validos para el mismo mail, y
                                   revocar uno no servia porque los otros
                                   seguian funcionando. Las vencidas no
                                   cuentan: ahi se puede volver a invitar.
GET    /api/invitacion            Lista invitaciones y su estado.
DELETE /api/invitacion/:id        Revoca una invitacion pendiente.
POST   /api/invitacion/aceptar    (publica) Crea la cuenta con el rol
                                   de la invitacion.
GET    /api/usuarios              Lista el staff.
PUT    /api/usuarios/:id          Edita un usuario (no al super_admin).
DELETE /api/usuarios/:id          Elimina un usuario (con las reglas
                                   de arriba).

9. REQUERIMIENTOS TECNICOS OBLIGATORIOS (lado backend)
============================================================
- Consumo de API REST: toda la app se sirve como API JSON en /api/*.
- Persistencia de datos: PostgreSQL (Supabase) via Prisma.
- Manejo de errores: middleware centralizado (errorHandler), respuestas
  JSON prolijas con status code correcto, nunca tira abajo el server.
- Validaciones en backend: formato de mail, longitud de contraseña,
  campos requeridos, estados validos, categoria existente, categoria
  con productos asociados no se puede borrar.
- Autenticacion y autorizacion: JWT + roles (requireRol) + reglas por
  usuario destino donde corresponde. Ver el detalle de las tres capas
  de seguridad mas abajo.
- Separacion frontend/backend: la API vive en /src y el frontend en
  /frontend (React + Vite). Son dos proyectos con su propio package.json y
  su propio .env; se hablan solo por HTTP.

Servidor base: Express, cors, morgan (logs), express.json(),
GET /api/health, archivos subidos servidos como estaticos en /uploads.

------------------------------------------------------------
9.1 CAPAS DE SEGURIDAD (en el orden en que actuan)
------------------------------------------------------------
Los pedidos pasan por cuatro filtros, del mas general al mas especifico.
Ademas, antes de todos ellos, helmet (src/app.js) agrega los headers de
seguridad estandar a toda respuesta: saca X-Powered-By (no publicamos que
corremos Express), nosniff, X-Frame-Options y HSTS. Se le desactiva una
sola cosa: Cross-Origin-Resource-Policy se pone en "cross-origin", porque
el default ("same-origin") haria que el navegador bloquee las imagenes de
/uploads cuando el frontend corre en otro puerto (localhost:5173).

CAPA 1 — CORS (que sitios web pueden consumir la API)
  Configurado en src/app.js con la variable de entorno CORS_ORIGINS:
  una lista de dominios separados por coma (ej.
  "http://localhost:5173,https://bsideclub.com"). Solo esos dominios
  reciben el header Access-Control-Allow-Origin.
  Metodos habilitados: GET, POST, PUT, PATCH, DELETE.
  Headers habilitados: Content-Type, Authorization, x-api-key.
  Si CORS_ORIGINS esta vacia o no existe, no se permite ningun dominio
  (nunca vuelve a "permitir todos") y el backend avisa por consola al
  arrancar.
  Ojo: CORS lo aplica el NAVEGADOR. Limita que paginas web pueden usar
  la API desde el browser, pero no frena pedidos hechos por fuera de un
  navegador (curl, Postman, scripts): esos siguen funcionando y no
  mandan header Origin.

CAPA 2 — LIMITE DE PEDIDOS POR IP (src/middlewares/rateLimit.js)
  Cuatro limites, segun que tan sensible es la ruta:

  - General: 300 pedidos cada 15 min, sobre todo /api. Es un techo alto, no
    esta pensado para frenar ataques puntuales sino para que un script suelto
    no pueda inundar el servidor. Va montado ANTES de la API key a proposito:
    si fuera despues, los pedidos sin clave se irian en 401 sin contar para el
    limite y se podria saturar el server igual.
  - Login (POST /api/auth/login): 10 intentos cada 15 min, y solo se cuentan
    los FALLIDOS (skipSuccessfulRequests). Asi el que entra bien sigue usando
    la app sin restricciones, y el que prueba contraseñas al azar se queda sin
    intentos enseguida. Esta es la proteccion real contra fuerza bruta.
  - Cuenta (register, forgot-password, reset-password, invitacion/aceptar):
    10 por hora. Son operaciones poco frecuentes por naturaleza, asi que el
    limite bajo no molesta el uso normal. En forgot-password ademas evita que
    se use la API para bombardear el mail de otra persona.
  - Formulario de contacto (POST /api/consultas): 5 por hora. Es publico y
    sin login, el vector de spam mas obvio de la API.

  Al pasarse, la respuesta es 429 con el mismo formato { error: "..." } que
  usa el resto de la API. Las rutas /api/* devuelven headers RateLimit-* para
  que el frontend sepa cuantos pedidos le quedan. GET /api/health queda
  afuera: esta registrado antes del limite, porque es el chequeo de que el
  servidor esta arriba y no tiene que poder agotarse.

  De donde sale la IP: NO de req.ip. Corriendo como funcion de Netlify no hay
  socket, asi que req.ip queda undefined y la libreria tiraba 500 en todos los
  pedidos al intentar usarlo. El identificador se arma a mano en
  src/middlewares/rateLimit.js leyendo el header x-nf-client-connection-ip
  (el que pone Netlify con la IP real del cliente), con x-forwarded-for de
  respaldo. Por eso ya no hace falta la variable TRUST_PROXY.

  LIMITACION IMPORTANTE en serverless: los contadores viven en memoria, y cada
  invocacion de la funcion puede arrancar en un contenedor nuevo. Netlify
  reutiliza contenedores un rato, asi que el limite funciona a medias, pero no
  es tan firme como en un servidor que queda prendido. Para que sea exacto
  habria que guardar los contadores afuera (en la base o en Redis).

CAPA 3 — API key interna (src/middlewares/apiKey.js)
  Montada con app.use('/api', requireApiKey). Lee el header x-api-key y
  lo compara contra la variable de entorno API_KEY usando
  crypto.timingSafeEqual (comparacion en tiempo constante, para no
  filtrar informacion por cuanto tarda la comparacion).
  - Falta el header o no coincide -> 401 "API key inválida o faltante".
  - API_KEY no configurada en el server -> 500 "API key no configurada
    en el servidor". Nunca deja pasar pedidos por falta de
    configuracion: si el .env esta mal armado, la API se cierra en vez
    de quedar abierta.
  Rutas que NO piden la clave, y por que:
  - GET /api/health: es el chequeo de que el servidor esta arriba,
    tiene que poder consultarse sin credenciales.
  - /uploads/*: son archivos estaticos (las imagenes de los productos).
    Una etiqueta <img> del navegador no puede mandar headers, asi que
    exigir la clave ahi romperia las imagenes del sitio. Ademas no
    cuelga de /api, asi que el middleware ni las toca.
  - El preflight OPTIONS del navegador: lo responde cors() antes de
    llegar a este middleware, porque cors() se monta primero.
  Importante: imagenRoutes esta montado directamente en /api
  (POST /api/productos/:id/imagenes, PATCH y DELETE /api/imagenes/:id),
  asi que tambien queda detras de la API key.

CAPA 4 — JWT + roles (lo que ya existia, sin cambios)
  requireAuth valida el token, requireRol chequea el rol, y algunos
  services agregan reglas segun el usuario destino (por ejemplo, no se
  puede tocar al super_admin). Ver seccion 8.

Que protege cada cosa (importante para no confiarse de mas):
  CORS y la API key filtran el uso desde otros sitios web y el uso
  casual de la API, pero la clave viaja en el frontend, asi que
  cualquiera que abra las herramientas del navegador puede leerla y
  reusarla con curl. No son un mecanismo de autenticacion.
  La proteccion real de las operaciones sensibles (crear/editar/borrar
  productos, categorias, usuarios, consultas) es el JWT con roles, que
  se sigue exigiendo igual que antes en todas esas rutas.
  Y lo que frena a alguien que ya tiene la clave y se pone a probar
  contraseñas es el limite de pedidos de la capa 2, no la clave.

Un detalle relacionado, en src/middlewares/errorHandler.js: los errores que
lanzamos nosotros traen .status y un mensaje escrito para el usuario, asi que
se devuelven tal cual. Los que NO traen status son inesperados (Prisma, bugs
nuestros) y su mensaje puede incluir detalles del schema o de la conexion a la
base: esos se reemplazan por un "Error interno del servidor" generico y el
detalle real queda solo en el log del servidor.

COMO CONSUMIR LA API DESDE EL FRONTEND (React + Vite)
============================================================
1. En el .env del proyecto de Vite (no en el del backend), definir:
       VITE_API_URL="http://localhost:3000/api"
       VITE_API_KEY="la misma clave que API_KEY del backend"
   Vite solo expone al frontend las variables que empiezan con VITE_.

2. Armar una unica funcion central de fetch y usarla siempre desde ahi,
   en vez de llamar a fetch() suelto en cada componente. Asi la clave y
   el token se mandan siempre y se configuran en un solo lugar:

       const API_URL = import.meta.env.VITE_API_URL;
       const API_KEY = import.meta.env.VITE_API_KEY;

       export async function api(ruta, opciones = {}) {
         const token = localStorage.getItem('token');

         const res = await fetch(API_URL + ruta, {
           ...opciones,
           headers: {
             'Content-Type': 'application/json',
             'x-api-key': API_KEY,
             ...(token ? { Authorization: `Bearer ${token}` } : {}),
             ...opciones.headers,
           },
         });

         if (!res.ok) throw new Error((await res.json()).error);
         return res.status === 204 ? null : res.json();
       }

   Nota: si se manda un FormData (subida de imagenes), NO poner
   Content-Type a mano — el navegador lo arma solo con el boundary.

3. El dominio desde el que corre el frontend tiene que estar si o si en
   CORS_ORIGINS del .env del backend, o el navegador bloquea todos los
   pedidos. En desarrollo Vite levanta en http://localhost:5173, que ya
   viene configurado; cuando se publique hay que agregar el dominio real.

4. Las imagenes de /uploads se pueden usar directo en un <img src="...">:
   no pasan por la API key.
